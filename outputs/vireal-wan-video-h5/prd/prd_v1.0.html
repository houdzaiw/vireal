Problem

一、需求背景

1.1 现状与痛点

用户侧

  • 普通用户希望快速将真人照片变为具有情绪价值的短视频，但专业视频编辑门槛高。
  • 通用模型需要反复编写提示词，动作不稳定、人物身份容易漂移。
  • 双人互动尤其容易出现站位混乱、肢体穿插和手部畸变。
  • 上传真人照片时，用户会关注隐私、保存时长和是否公开。

业务侧

  • 现有 Vireal 项目具备后端、订单事件和后台基础，但没有用户 H5、生成任务和 OSS。
  • 视频生成耗时且成本明显高于普通 API，需要可追踪的异步任务和金币账本。
  • 个人项目缺少境外公司主体，首期直接接 Stripe 或国内支付会增加准入成本。
  • 真人生成涉及肖像授权、内容审核和支付渠道风控，必须在产品入口前置治理。

1.2 为什么现在做

Replicate 当前提供 Wan 2.7 R2V、Seedance 2.0 和 Wan 2.2 Animate：前两者作为双人参考图候选，后者把固定动作视频迁移到单张人物图片。Wan R2V 最长 10 秒且多主体效果必须实测；双人 15 秒仅在 Seedance PoC 通过后开放。

1.3 产品定位

一句话定位：面向海外个人用户的私密真人照片动作视频生成工具。

首期不做：中国大陆注册与付费、公开社区、站内分享、用户自定义提示词、用户上传动作视频、多人以上生成、原生 iOS/Android 应用。

2.1 MVP 验收口径

  • 用户可使用 Apple、Google 或邮箱验证码登录，且同一邮箱能够正确归并账号。
  • 用户可完成一人/两人照片上传、质量校验、授权声明、模板和时长选择。
  • 系统提交异步生成任务后，用户离开页面不会中断生成。
  • 成功任务产生一个视频；任何失败终态只返还一次本次扣除金币。
  • PayPal 支付成功只增加一次金币，伪造或重复 webhook 不得重复入账。
  • 视频只对所有者授权访问，到期和主动删除后均无法继续访问。
Audience

三、用户与使用场景

3.1 典型用户

海外华人情侣

希望把两张个人照片制作成拥抱或牵手短视频，保存纪念，不希望作品公开。

个人娱乐用户

希望用自己的全身照快速制作跳舞、运动短视频，用于个人观看或下载保存。

轻度创作用户

不会写提示词，希望选择动作、时长即可完成生成，愿意为更长视频购买金币。

3.2 核心使用场景

  • 双人纪念：用户分别上传两张独立单人全身照，生成拥抱或牵手视频。
  • 单人娱乐：用户上传自己的全身照，生成固定舞蹈视频。
  • 运动趣味：用户上传全身照，生成规范俯卧撑动作视频。
  • 后台等待：提交任务后关闭页面，稍后重新登录查看作品。
  • 短期下载：用户在24小时内播放、下载或主动删除作品。

  3. 上传素材通过格式、人数、全身完整度和内容审核。

  5. 金币余额不少于所选时长价格。
  6. 模板、模型和所在区域均处于可用状态。

Detailed Solution

五、详细方案

原型评审结论：2026-09-09 已确认动作优先的信息架构，以及登录、上传、授权、扣币、异步生成、失败返币、作品与 PayPal 的完整交互。下列切片均引用同版本原型，并启用 Focus 模式锁定无关区域。

规则与反馈

  • 地区校验：前端提示与服务端拦截同时执行；中国大陆用户只能浏览落地页，登录、购买和生成接口返回地区不可用。
  • 登录排序：iPhone 默认将 Apple 放在首位，Android 默认将 Google 放在首位，三种方式始终全部可选。
  • 邮箱验证：验证码一次有效、短时过期，并按邮箱、IP 和设备进行发送限流。
  • 新用户赠送：首次创建有效账户时幂等发放 30 金币；重复登录不得重复领取。

规则与反馈

  • 声明内容：人物均年满 18 周岁；为本人或已经明确授权；禁止冒充、欺诈、骚扰、色情和诽谤用途。
  • 审计证据：声明版本、语言、内容哈希、确认时间和脱敏 IP 与生成任务绑定，非媒体记录保留 180 天。
  • 审核：输入与输出均进行内容审核；疑似未成年人、公众人物冒充或高风险内容拒绝处理。
  • 产品边界：不要求上传身份证、授权书或活体视频，首期仅保留声明、审核和投诉追溯能力。

04时长扣币、异步生成与失败返还

交互逻辑

flowchart TD select([选择时长]) balance{余额充足?} buy[进入金币购买] debit[原子扣除金币] submit[创建异步任务] terminal{最终状态?} save[保存私有视频] refunded{已返币?} refund[全额返还] done([作品记录展示]) select --> balance balance -->|否| buy balance -->|是| debit debit --> submit submit --> terminal terminal -->|成功| save terminal -->|失败| refunded refunded -->|否| refund refunded -->|是| done refund --> done save --> done

规则与反馈

  • 定价：5 秒 30 金币、10 秒 40 金币、15 秒 50 金币；一次生成只输出一个结果。
  • 提交事务：生成任务、扣币流水和幂等键在同一事务内创建；按钮提交后立即禁用，避免重复任务。
  • 后台处理：用户可离开当前页面；客户端只展示阶段与预计等待，不承诺精确百分比。
  • 失败返还：审核拒绝、模型失败、超时、结果转存或后审失败均全额返还；唯一键 task_id + ledger_type 保证最多返还一次。
  • Replicate 临时地址：结果成功后由 Worker 立即转存私有 OSS，H5 不接触 API Token，也不直接依赖 replicate.delivery。

  • 私有访问：所有查询、播放、下载和删除都验证当前用户与作品所有权，不提供公开分享链接。
  • 作品状态：处理中展示阶段；成功展示播放器、下载和倒计时；失败展示原因和已返金币。
  • 主动删除：二次确认后立即撤销签名 URL 和页面访问，输入、输出进入清理队列且不可恢复。
  • 自动到期：结果生成后 24 小时清理媒体及作品记录；OSS Lifecycle 作为应用任务失败时的兜底。
  • 断网恢复：页面断网只影响状态刷新，服务端任务继续；重新登录后从作品记录恢复最终状态。

交互逻辑

flowchart TD pack([选择金币包]) order[创建待支付订单] paypal[PayPal 收银台] webhook[接收服务端通知] verify{验签及金额有效?} seen{事件已处理?} credit[原子写入购买流水] pending[保持处理中] success([展示到账]) pack --> order order --> paypal paypal --> webhook webhook --> verify verify -->|否| pending verify -->|是| seen seen -->|是| success seen -->|否| credit credit --> success

规则与反馈

  • 金币包：USD 5.99 购买 100 金币；USD 11.99 购买 220 金币；USD 24.99 购买 500 金币。
  • 到账依据：前端支付完成页不能入账；只有后端验证 PayPal webhook 或主动查询交易成功后才能增加金币。
  • 支付幂等：外部事件 ID 与交易 ID 建唯一约束，重复通知直接返回成功但不重复入账。
  • 账本：新用户赠送、购买、生成扣除、失败返还、人工调整和支付退款冲销都写不可变流水。
  • 支付地区：币种固定 USD；受限地区用户无法创建订单，服务端再次验证地区及账户风控状态。
