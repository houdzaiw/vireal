Product Requirements Document

App 服务端与后台管理系统 PRD v1.0

本 PRD 面向第一版本地/内网可运行的服务端与后台管理系统，目标是在较短周期内跑通移动 App 设备号登录、用户资料、动态内容、图片上传、订单回调、后台管理与 key-value 配置能力。

推荐技术底座FastAPI Full-Stack Template 二次开发，保留 FastAPI、PostgreSQL、Docker Compose、React 后台。
项目拆分策略服务端与后台管理放在 server 项目；移动 App 单独项目，只调用 API。
第一版原则快速上线、功能可用、逻辑清晰，暂不追求复杂权限、多租户、高可用和精细运营。
账号体系原则后台管理员与 App 用户完全独立，不共用用户表。

一、需求背景

项目需要为移动 App 提供一套稳定、可快速开发的服务端 API，同时需要一个后台管理系统用于查看和管理 App 用户、用户生成内容、订单状态以及运营配置。开发者具备 Python 开发能力，希望尽量复用成熟脚手架，减少登录、数据库、Docker、前后端联调等基础工程的搭建成本。

现阶段最大的痛点不是复杂业务，而是需要快速形成一套能跑通闭环的基础平台：App 可以无注册成本进入，用户可以发布文字和图片动态，后台可以处理异常用户和内容，支付平台的订阅或内购状态可以同步到后端，运营配置可以在 App 启动时下发。

为什么现在做

  • 移动 App 需要尽快进入可用验证阶段，不能被复杂账号体系和后台工程拖慢。
  • 设备号登录能够降低第一版注册门槛，适合快速验证内容和支付链路。
  • 后台管理系统需要尽早存在，否则用户内容、订单、配置和异常状态无法闭环处理。
  • Apple IAP 和 Google Play 支付状态需要由服务端统一记录，避免只依赖客户端状态造成订单不一致。

技术选型判断

使用 FastAPI Full-Stack Template 二次开发是合理的。它提供 FastAPI 后端、PostgreSQL、Docker Compose、React 管理前端、JWT 登录、基础用户管理和测试结构，适合作为后台管理和 API 服务底座。需要注意的是，模板原生用户体系主要面向账号密码登录，应保留给后台管理员使用；App 用户需要单独建表，并通过设备 UUID 登录。

阶段 用户触点 用户行为 痛点/情绪 产品机会点

退出或换设备 App 设置页、新设备 退出登录或设备 UUID 变化。 第一版接受新设备产生新账号。 服务端以设备 UUID 为身份边界，不提供账号找回。

四、需求功能清单

模块 功能点 优先级 基础逻辑 前置条件 数据流向
项目底座 FastAPI 模板二次开发 P0 保留模板后端、数据库、Docker、React 后台；将原用户体系定位为后台管理员体系。 初始化模板项目，确认环境变量、数据库连接和本地启动命令。 开发者启动 Docker Compose，后端连接 PostgreSQL，后台前端调用后端 API。
后台账号 管理员账号密码登录 P0 第一版仅一个管理员角色，管理员可访问所有后台功能。 创建初始超级管理员账号。 后台登录页提交账号密码，后端校验后返回管理端 token。
App 登录 设备 UUID 登录 P0 App 提交设备 UUID；若不存在则创建新 App 用户；若存在则返回原 App 用户。设备号变化即创建新用户。 App 能稳定生成或读取设备 UUID。 App -> 设备登录接口 -> app_users/app_devices -> 返回长期 token 和用户资料。
App 用户资料 修改头像、昵称 P0 App 用户只能修改自己的头像和昵称；后台不能代改用户资料。 App 用户已登录。 App 上传头像到本地文件目录，后端保存文件路径并更新 app_users。
图片存储 本地文件存储 P0 第一版头像和动态图片存储在服务端本地目录，后端提供可访问 URL。 部署环境挂载上传目录，限制文件类型和大小。 App -> 上传接口 -> 本地 uploads 目录 -> 文件元数据入库。
动态内容 发布文字/图片动态 P0 用户发布后立即展示，不走审核；内容支持文字和图片组合。 App 用户已登录，上传内容满足长度和图片限制。 App -> 发布接口 -> contents/content_images -> 动态流接口返回。
动态内容 动态列表与详情 P0 列表默认排除已删除内容、禁用用户内容和禁用内容，不显示删除占位。 存在已发布内容。 App -> 列表接口 -> 按时间分页返回内容、作者资料和图片 URL。
后台用户管理 查看、禁用、删除 App 用户 P0 后台可查看用户状态和基础资料；禁用后用户不能继续发布；删除使用软删除。 管理员已登录。 后台 -> 管理 API -> 更新 app_users 状态；App API 根据状态拦截或过滤。
后台内容管理 查看、删除动态 P0 后台删除动态后，App 列表和详情不再返回该内容；不保留“已删除”占位。 管理员已登录，动态存在。 后台 -> 内容管理 API -> 更新 contents.deleted_at/status -> App 查询过滤。
订单 Apple IAP 与 Google Play 支付通知接收 P0 后端提供平台通知入口，记录原始通知摘要，更新订单状态。第一版重点是状态可落库、可查看。 配置 Apple/Google 通知地址和必要密钥；本地/内网阶段可先用模拟通知验证。 Apple/Google -> webhook -> orders/order_events -> 后台订单页展示。
后台订单管理 订单状态查看 P0 后台可查看订单号、平台、用户、金额或商品、状态、最近更新时间和错误信息。 存在订单记录或支付通知。 后台 -> 订单管理 API -> orders/order_events。
运营配置 key-value 配置管理 P0 后台可新增、编辑、启用、停用配置；App 启动时拉取所有启用配置。 管理员已登录。 后台 -> configs 表；App 启动 -> 配置接口 -> 返回启用配置。
安全与限制 基础接口鉴权与输入校验 P1 管理端和 App 端 token 分开；关键接口校验文件类型、图片大小、昵称长度、内容长度。 后端定义统一错误结构。 客户端请求 -> 鉴权依赖 -> 业务接口 -> 统一错误响应。
日志 关键业务日志 P1 记录登录、内容删除、用户禁用、订单通知处理、配置变更等关键操作。 确定日志落点，第一版可先用应用日志和数据库事件表。 业务操作 -> 日志/事件记录 -> 后台排查。

五、详细方案

本章节将在原型确认后补充每个功能模块的交互流程图、规则描述和 iframe 原型沙盒切片。当前版本先记录基础业务逻辑，避免在未看到界面前过早固化交互细节。

模块 1：App 设备号登录

当前基础规则：App 提交设备 UUID 和平台信息；服务端按设备 UUID 查找绑定关系，不存在则创建 App 用户和设备记录；返回长期 App token。用户主动退出后客户端删除 token，服务端可记录退出时间。第一版不支持账号找回，换设备或设备号变化即生成新用户。

待原型确认后补充：设备号登录流程图、异常提示、专注模式原型切片。

模块 2：头像昵称修改

当前基础规则：App 用户只能修改自己的头像和昵称；头像文件本地保存，数据库保存可访问 URL；昵称需限制长度并过滤空值。后台不提供代改资料能力。

待原型确认后补充：资料页交互、上传失败提示、保存成功反馈。

模块 3：动态发布与浏览

当前基础规则：动态支持文字和图片，发布后立即进入动态流；后台删除后 App API 不再返回；不展示“内容已删除”占位。禁用用户后，该用户不能继续发布，其内容是否全部隐藏需在原型阶段进一步确认，默认隐藏。

待原型确认后补充：发布页、动态流、图片预览、失败重试和删除后的展示逻辑。

模块 4：后台管理

当前基础规则：管理员账号密码登录后台；第一版只有一个管理员角色。后台包含 App 用户管理、动态内容管理、订单状态查看、运营配置管理四个核心菜单。

待原型确认后补充：后台列表、筛选、删除确认、禁用确认、配置编辑弹窗。

模块 5：支付回调与订单状态

当前基础规则：后端接收 Apple IAP 和 Google Play 通知，记录平台、交易号、商品 ID、状态和事件摘要。第一版本地/内网可先通过模拟通知验证流程；真实生产接入时再补齐签名校验、通知重放处理和平台 API 二次校验。

待原型确认后补充：订单详情页、通知事件列表、异常状态说明。

模块 6：key-value 配置

当前基础规则：后台维护 key、value、类型、启用状态和描述；App 启动时拉取所有启用配置。第一版不做灰度、不做版本化、不做按地区或 App 版本差异下发。

待原型确认后补充：配置列表、编辑状态、启停反馈和 App 拉取异常处理。

七、异常与边界处理

场景 处理规则 第一版要求
设备 UUID 为空或格式异常 拒绝登录，返回明确错误码和错误信息。 必须处理
设备 UUID 变化 视为新设备和新用户，不做账号找回。 必须处理
App 用户被禁用 禁止发布动态；登录和资料接口可返回用户状态，App 端据此拦截。 必须处理
图片上传失败 返回失败原因；不创建依赖该图片的动态。 必须处理
图片类型或大小不合法 限制为常见图片类型，并设置大小上限。 必须处理
动态已删除 App 列表和详情不返回，不显示占位。 必须处理
支付通知重复 按平台交易号或事件 ID 做幂等处理。 建议处理
支付通知无法匹配订单 记录异常事件，后台可查看，后续可人工排查。 建议处理
配置为空 App 配置接口返回空对象或空数组，App 使用默认值。 必须处理
后台误删内容 第一版使用软删除，数据库保留记录，暂不提供恢复入口。 建议处理

八、数据追踪与埋点

第一版以服务端业务日志和数据库记录为主，不强制接入第三方埋点平台。建议保留以下关键事件，便于排查和后续增长分析。
